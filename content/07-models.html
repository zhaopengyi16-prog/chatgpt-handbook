7.2 方案架构

7.2.1 总体架构

本方案使用官方 Codex App 或 Codex CLI 作为操作界面，通过本地 OpenCodex 网关访问不同的模型供应商。

可复制提示词
Codex App / Codex CLI
          │
          ▼
http://127.0.0.1:10100
          │
          ▼
      OpenCodex
      ├─ OpenAI
      ├─ DeepSeek
      ├─ Claude
      └─ 其他 Provider

各组件职责如下：

  • Codex App / Codex CLI：提供官方 Codex 操作界面和命令行能力。
  • OpenCodex：负责模型目录管理、请求路由和协议转换。
  • Provider：提供具体模型和推理服务。

需要注意：

  • Codex App 仍然是官方客户端。
  • OpenCodex 位于 Codex 与模型供应商之间。
  • 启用 OpenCodex 后，请求不再属于纯官方直连链路。

恢复官方直连时，按当前 OpenCodex 文档停止代理并检查恢复后的客户端配置与实际请求链路。

7.3 DeepSeek 接入方式选择

可以选择供应商提供的接入方式，也可以采用第三方本地网关。先确认当前文档、支持入口和自己能维护的组件。

7.3.1 方案 A：供应商直接接入

架构如下：

可复制提示词
Codex
  │
  ▼
DeepSeek API

适用特点：

认证通常采用供应商支持的方式；是否需要 ChatGPT 登录，按实际入口与配置确认。

  • 配置步骤较少。
  • 请求链路较短。
  • 适合主要或仅使用 DeepSeek 的场景。
  • 切换回 GPT 时，通常需要恢复或重新修改 Codex 配置。
  • 不适合作为多个模型供应商的统一管理入口。
原稿提到的 DeepSeek 专用脚本页面本次未能成功核对，以下仅保留方案比较，不把旧脚本当作已验证的安装方法。

7.3.2 方案 B：OpenCodex 多模型网关

架构如下：

可复制提示词
Codex
  │
  ▼
OpenCodex
  ├─ GPT
  ├─ DeepSeek
  ├─ Claude
  └─ 其他模型

适用特点：

  • 可以保留 GPT 的 ChatGPT 订阅链路。
  • DeepSeek、Claude 等模型可以使用各自的 API Key 或 OAuth 凭据。
  • 可以通过同一个 Codex 模型选择器切换模型。
  • 适合不同模型分工协作。
  • 需要维护本地服务、Provider 配置和模型目录。

7.3.3 选择建议

使用需求推荐方式
仅使用 DeepSeek供应商当前支持的直接接入方式
经常在 GPT 与 DeepSeek 之间切换OpenCodex
规划、执行与复核使用不同模型OpenCodex
优先考虑最低维护成本供应商当前支持的直接接入方式
公司统一管理多个模型供应商OpenCodex 或企业统一网关

两种方案的定位区别如下：

直接接入减少链路组件；本地网关便于统一管理多个供应商，但需要维护服务、认证与模型路由。

7.4 标准部署流程

本节给出安装与验收顺序。当前公开版尚未完成各客户端版本的实机复测；涉及旧版服务和同步命令的部分，按实际版本帮助确认。

参考：OpenCodex 当前 README

7.4.1 检查基础环境

在 PowerShell 中执行：

PowerShell 示例
node -v
npm -v
codex --version
ocx --version

应确认以下组件均可正常执行：

  • Node.js
  • npm
  • Codex CLI
  • OpenCodex CLI

如果 Codex CLI 或 OpenCodex 尚未安装，应继续执行后续安装步骤。

7.4.2 安装 Codex CLI

PowerShell 示例
npm install -g @openai/codex

安装完成后验证：

PowerShell 示例
codex --version

7.4.3 安装 OpenCodex

PowerShell 示例
npm install -g @bitkyc08/opencodex

安装完成后验证：

PowerShell 示例
ocx --version

7.4.4 启动代理并初始化

当前项目文档区分启动与初始化：ocx start（或服务方式）启动代理；ocx init 写入配置，初始化本身不启动代理。

当前文档中的命令
ocx start
# 在另一个终端中按需初始化
ocx init
ocx status
  • OpenAI 或 ChatGPT 登录方式。
  • 本地监听端口，建议使用 10100。
  • Codex Home 目录。
  • 是否安装后台服务。
  • 默认 Provider 和默认模型。

初始化完成后，应确认 OpenCodex 配置文件已经生成。

7.4.5 安装并启动后台服务

如需后台服务，先查看当前版本支持的服务操作及安装方式：

先检查当前版本
ocx service --help
ocx status

正常状态应包含：

验收目标
代理处于运行状态
本地健康检查通过
实际监听地址与客户端配置一致

如果服务未运行，应优先解决服务层问题，不要直接进入 Codex App 测试。

7.4.6 添加第三方 Provider

以 DeepSeek 为例：

按交互提示添加 Provider
ocx provider add deepseek

在服务提供的凭据输入界面填写 API Key。不要把真实值放到聊天或公开命令中。命令参数和安全输入方式按当前版本帮助确认。

完成后执行：

检查已配置的供应商
ocx provider list

应确认 DeepSeek 位于已配置的 Provider 列表中，而不仅是出现在可用 Provider 注册表中。

7.4.7 重启服务并加载最新配置

配置变更后检查运行实例是否已加载新配置。若需要重启，使用所安装版本支持的服务管理方式。

查询服务操作并检查状态
ocx service --help
ocx status

原因如下：

Provider 配置虽然已经写入配置文件，但正在运行的后台进程可能仍然保留旧的内存配置。重启服务可以确保最新的 Provider、认证信息和模型映射被重新加载。

不要把服务安装当作每次配置更新后的常规步骤。先查看所用版本支持的操作：

确认服务管理方式
ocx service --help

重新安装服务可能重新生成服务启动脚本，并覆盖已有的本地调整。仅在服务未安装或服务定义损坏时，才应重新执行安装操作。

7.4.8 同步模型目录

确认模型目录已同步到当前客户端，具体同步动作以所用版本帮助与界面为准：

查看当前命令与状态
ocx --help
ocx status

然后检查 Codex 配置：

PowerShell 示例
Select-String `
  -Path "$HOME\.codex\config.toml" `
  -Pattern 'openai_base_url|model_catalog_json'

正常配置示例：

TOML 示例
model_catalog_json = "C:\\Users\\<USER_NAME>\\.codex\\opencodex-catalog.json"
openai_base_url = "http://127.0.0.1:10100/v1"

其中 <USER_NAME> 应为当前 Windows 用户名。

7.5 分层验收流程

安装完成后，不应直接以 Codex App 的运行结果作为唯一验收依据。

正确方式是从服务层、Provider 层和网关层开始，逐级向上验证。只有当前层级验证成功后，才进入下一层级。

7.5.1 第一级：服务健康检查

执行：

PowerShell 示例
ocx status

必须确认：

可复制提示词
Proxy: running
Health: ok

如果 Proxy 未运行或健康检查失败，应先处理 OpenCodex 服务问题。

7.5.2 第二级：Provider 配置检查

执行：

检查供应商
ocx provider list

DeepSeek 配置应包含与以下内容等效的信息：

可复制提示词
adapter: openai-chat
authMode: key
baseUrl: https://api.deepseek.com

重点确认：

  • Provider 已配置。
  • Provider 名称正确。
  • 认证模式为 API Key。
  • Base URL 指向正确的供应商地址。
  • API Key 已成功写入或关联。

7.5.3 第三级：直接测试本地网关

使用 PowerShell 直接请求 OpenCodex：

PowerShell 示例
$body = @{
    model  = "deepseek/deepseek-chat"
    input  = "只回复 OK"
    stream = $false
} | ConvertTo-Json

Invoke-RestMethod `
    -Uri "http://127.0.0.1:10100/v1/responses" `
    -Method Post `
    -ContentType "application/json" `
    -Body $body

成功结果应包含：

可复制提示词
status : completed
model  : deepseek-chat

本层测试绕过了 Codex App 和 Codex CLI，可以直接验证：

  • 请求是否能够到达 OpenCodex。
  • OpenCodex 是否正确识别模型名称。
  • Provider 是否被正确加载。
  • API Key 是否有效。
  • 模型路由是否正确。
  • 供应商接口是否能够正常返回结果。

如果本层失败，不应继续排查 Codex App。

7.5.4 第四级：Codex CLI 测试

执行：

PowerShell 示例
codex -m "deepseek/deepseek-chat" "只回复 OK"

应确认：

  • Codex CLI 可以访问本地 OpenCodex 网关。
  • 指定的模型名称可以被正确识别。
  • 请求可以正常完成。

如果本地网关测试成功，但 Codex CLI 测试失败，应重点检查：

  • $HOME\.codex\config.toml
  • openai_base_url
  • model_catalog_json
  • 系统代理和 NO_PROXY
  • Codex CLI 是否读取了正确的用户配置目录

7.5.5 第五级：Codex App 测试

完成前四级验证后：

  1. 完全关闭 Codex App。
  2. 重新启动 Codex App。
  3. 在模型选择器中选择：
可复制提示词
deepseek/deepseek-chat
  1. 发送简单测试任务，例如：
可复制提示词
只回复 OK

如果模型目录已更新但 Codex App 中没有显示新模型，应重新启动 App，必要时再次执行：

PowerShell 示例
ocx --help
ocx status

7.5.6 第六级：确认实际 Provider 和模型

不要通过向模型提问以下内容来判断实际模型：

可复制提示词
你是什么模型？

该方法不可靠。Codex App 可能向底层模型注入角色、身份和运行环境提示，因此模型可能回答：

可复制提示词
我是 Codex。

或：

可复制提示词
我是 OpenAI 的编程助手。

正确的确认方式是查看 OpenCodex Dashboard 中记录的实际请求信息：

可复制提示词

Model: deepseek-chat

也可以查看 Provider 日志：

查询当前调试与日志命令
ocx debug --help

模型身份应以实际请求日志中的 Provider 和 Model 字段为准。

7.6.1 故障 A：访问本地网关时返回 502

故障现象

Codex CLI 或其他客户端返回：

可复制提示词
unexpected status 502 Bad Gateway
url: http://127.0.0.1:10100/v1/responses

同时可能出现以下情况：

  • ocx status 显示 OpenCodex 服务正常。
  • OpenCodex Dashboard 中没有对应请求。
  • Provider 调试日志中没有请求记录。

判断依据

没有对应日志时，先核对日志是否启用、时间范围、服务实例及实际请求地址，再判断请求是否到达。

直接原因

本地地址被系统代理接管是一个候选原因，也可能是上游服务、路由或网络故障。以下 NO_PROXY 方法仅用于验证本地地址代理问题。

临时验证方法

在当前 PowerShell 会话中设置：

PowerShell 示例
$env:NO_PROXY = "127.0.0.1,localhost"
$env:no_proxy = "127.0.0.1,localhost"

然后重新测试：

PowerShell 示例
codex -m "<MODEL_NAME>" "只回复 OK"

如果设置后请求恢复正常，说明代理绕过配置可能与问题有关；再次复现并结合日志确认，排除同时发生的其他变化。

永久处理方法

设置用户级 NO_PROXY 环境变量，并保留已有配置：

PowerShell 示例
$current = [Environment]::GetEnvironmentVariable("NO_PROXY", "User")

$entries = @()

if ($current) {
    $entries += $current -split ","
}

$entries += "localhost", "127.0.0.1", "::1"

$value = (
    $entries |
    ForEach-Object { $_.Trim() } |
    Where-Object { $_ } |
    Select-Object -Unique
) -join ","

[Environment]::SetEnvironmentVariable(
    "NO_PROXY",
    $value,
    "User"
)

设置完成后，应关闭并重新打开以下程序，使环境变量生效：

  • PowerShell
  • Codex CLI 所在终端
  • Codex App
  • 其他调用 OpenCodex 的客户端

验证方法

重新执行本地网关测试：

PowerShell 示例
Invoke-RestMethod `
    -Uri "http://127.0.0.1:10100/healthz" `
    -Method Get

然后执行 Codex CLI 测试。

预防措施

所有安装了以下软件或配置的计算机，在部署 OpenCodex 前都应检查本地地址代理绕过设置：

  • Clash
  • VPN 客户端
  • 企业网络代理
  • 系统级 HTTP 或 HTTPS 代理
  • 终端环境变量代理

本地绕过列表至少应包含：

可复制提示词
localhost
127.0.0.1
::1

7.6.2 故障 B：系统重启后 DeepSeek 模型消失

故障现象

Codex 模型列表中不再显示 DeepSeek。

执行：

PowerShell 示例
ocx provider list

已配置列表中只显示：

可复制提示词
openai (default)

而 DeepSeek 仅出现在：

可复制提示词
Available from registry

判断依据

“Available from registry”只表示当前版本的 OpenCodex 支持该 Provider，不表示用户已经完成 Provider 配置。

只有出现在已配置 Provider 列表中的 Provider 才能被实际使用。

已确认事实

发生问题时，本地已配置 Provider 列表中不存在 DeepSeek。

现有证据不足以进一步确认具体原因属于以下哪一种：

  • Provider 配置被覆盖。
  • Provider 配置未正确持久化。
  • Provider 添加流程未最终完成。
  • OpenCodex 读取了其他用户目录或配置目录。

因此，不应在指南中写成：

可复制提示词
Windows 重启会导致 DeepSeek Provider 丢失。

该结论目前没有充分证据支持。

处理方法

重新添加 Provider：

重新配置前先检查已有状态
ocx provider add deepseek

确认配置：

检查供应商
ocx provider list

重启服务：

按当前版本管理服务
ocx service --help

重新同步模型目录：

在当前版本支持的入口同步模型目录，再检查客户端读取的配置。

验证方法

依次执行：

核对已配置的 Provider
ocx provider list

然后直接测试本地网关：

PowerShell 示例
$body = @{
    model  = "deepseek/deepseek-chat"
    input  = "只回复 OK"
    stream = $false
} | ConvertTo-Json

Invoke-RestMethod `
    -Uri "http://127.0.0.1:10100/v1/responses" `
    -Method Post `
    -ContentType "application/json" `
    -Body $body

预防措施

部署和验收完成后，建议备份以下文件：

可复制提示词
%USERPROFILE%\.opencodex\config.json
%USERPROFILE%\.codex\config.toml
%USERPROFILE%\.codex\opencodex-catalog.json

安全要求：

配置文件中可能包含 API Key、Token 或其他认证信息。备份文件应按照敏感资料管理，不得上传到公共代码仓库、公共网盘或未经授权的共享目录。

7.6.3 故障 C：模型可见，但提示 ChatGPT 账户不支持

故障现象

模型已经出现在 Codex 模型列表中，但调用时返回：

JSON 示例
{
  "detail": "The 'deepseek/deepseek-chat' model is not supported when using Codex with a ChatGPT account."
}

容易产生的误判

该错误表面上容易被理解为：

可复制提示词
Codex App 不允许使用 ChatGPT 账户调用 DeepSeek。

但仅凭 Codex App 中的错误信息，无法确定问题发生在哪一层。

判断方法

直接请求本地 OpenCodex 网关：

PowerShell 示例
$body = @{
    model  = "deepseek/deepseek-chat"
    input  = "只回复 OK"
    stream = $false
} | ConvertTo-Json

Invoke-RestMethod `
    -Uri "http://127.0.0.1:10100/v1/responses" `
    -Method Post `
    -ContentType "application/json" `
    -Body $body

如果本地网关返回相同错误，可以确认：

  • 请求已经到达 OpenCodex。
  • 问题不只存在于 Codex App 层。
  • OpenCodex 没有按照预期将请求路由到 DeepSeek。

原案例中的原因判断

原案例中，重启后恢复，怀疑运行进程没有加载新 Provider 配置。相同报错也可能来自路由或认证设置，需用实际记录定位，不能仅凭报错认定原因。

以下是与原案例现象相符的一种路由假设，需要用实际请求记录核实：

可复制提示词
deepseek/deepseek-chat
        │
        ▼
OpenCodex 未识别 DeepSeek Provider
        │
        ▼
回落到默认 OpenAI Provider
        │
        ▼
OpenAI 后端拒绝 DeepSeek 模型名称

处理方法

重启 OpenCodex 服务：

按当前版本查询重启方式
ocx service --help

验证方法

重新执行本地网关测试。

成功结果应包含：

可复制提示词
status : completed
model  : deepseek-chat

本地网关成功后，再依次测试 Codex CLI 和 Codex App。

预防措施

发生以下变更后，应检查运行实例加载情况，并在所用版本需要时重启服务：

  • 新增 Provider。
  • 修改 Provider。
  • 更新 API Key。
  • 修改 Provider Base URL。
  • 修改模型映射。
  • 修改默认 Provider。
  • 修改默认模型。
  • 修改与请求路由相关的配置。

7.6.4 故障 D：模型自我描述与实际模型不一致

故障现象

在 Codex App 中已经选择 DeepSeek，但模型回答：

可复制提示词
我是 Codex，OpenAI 的编程助手。

原因

Codex App 会向底层模型注入角色说明、工作环境和系统提示。模型的自我描述可能受到这些提示影响。

因此，模型对自身身份的回答不属于可靠的技术证据。

处理方法

通过以下方式确认实际调用链路：

  1. 查看 OpenCodex Dashboard。
  2. 查看 Provider 请求日志。
查询当前日志入口
ocx debug --help

验证标准

以请求记录中的以下字段为准：

可复制提示词
Provider
Model
Base URL
HTTP 状态
请求完成状态

例如：

7.7 多模型协作方式

OpenCodex 的主要价值之一，是让不同模型通过统一入口参与同一个工程流程。

推荐的模型分工如下：

需要明确：

OpenCodex 提供的是多模型目录和请求路由能力，不等同于自动多代理编排系统。

不同模型之间不应依赖彼此不可见的上下文或“思考过程”，而应通过工程文件进行交接。

7.8 附录：典型故障处理时间线

以下按原作者记录整理，保留当时的排查过程。本次未重现环境，不将其中的原因推断视为已独立验证：

可复制提示词
1. Codex 请求本地 10100 端口时返回 502。
2. 在当前终端设置临时 NO_PROXY 后，Codex CLI 恢复。
3. 将本地地址加入用户级 NO_PROXY，完成永久代理绕过配置。
4. 系统重启后，发现 DeepSeek 不在已配置 Provider 列表中。
5. 重新添加 DeepSeek Provider。
6. DeepSeek 模型可以显示，但出现账户不支持的报错。
7. 直接请求本地 OpenCodex 网关，复现相同错误。
8. 重启 OpenCodex 后台服务。
9. 本地网关返回 deepseek-chat 和 completed。
10. Codex CLI 与 Codex App 恢复正常使用。

对这段历史记录，可以做以下分层判断：

可复制提示词
502 问题
  └─ 修改代理绕过设置后恢复，需结合当时配置确认

Provider 消失问题
  └─ 已配置列表中不存在 DeepSeek
     具体丢失原因尚未完全确认

账户不支持问题
  └─ 重启后台服务后恢复
     旧配置或路由回落是候选原因，仍需日志证据
