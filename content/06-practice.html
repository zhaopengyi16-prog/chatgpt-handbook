该章节旨在让读者更好的利用Codex这个工具，其中会提供一些实际的相关案例供大家参考，当然不必拘泥于章节的一些固定做法，一切只是为了使相关概念更好理解，我更期望读者在消化完后能拥有属于自己的一套工作流程。

6.1 理解 Skill

在前面的 3.7章节中，我们已经对 Skill 的作用和使用效果进行了简单介绍。

为了帮助读者进一步理解，本节将结合个人实际使用经验，再次对 Skill 的功能、价值和使用方式进行说明。

温故而知新。 本节不要求读者理解 Skill 的全部技术细节，只需要理解它能够解决什么问题，以及什么时候适合使用 Skill。

6.2 Skill 界面与工程初始化案例

Skill 将一个重复任务的步骤、资料和输出要求整理成可复用的流程。它可以减少反复说明同一套要求的工作。

参考：官方 Skill 说明

与其每次都重新向 ChatGPT 描述完整需求，不如将经常重复使用的步骤、规则和资料提前封装起来。以后遇到类似任务时，便可以直接调用对应的 Skill。

因此，Skill 的价值不只是“保存一段提示词”，而是将以下内容组合成一套稳定的执行方法：

  • 工作步骤；
  • 约束规则；
  • 输出格式；
  • 专业资料；
  • 工程模板；
  • 自动化脚本；
  • 检查和验证流程。

  • 原始工程源码；

  • 芯片及外设信息；
  • 通信接口要求；
  • 软件架构要求；
  • 构建和测试方式。

然后调用对应的 Skill，Codex 就可以根据既定流程，对工程进行初始化和增量更新。

整个过程可以概括为：

输入项目资料

      ↓

一个设计合理的工程 Skill，应当在关键步骤设置确认点，并明确区分：

  • 可以自动完成的内容；
  • 需要工程师批准的内容；
  • 必须由工程师在实机上验证的内容。

当一个工程中存在经常重复使用的提示词、操作步骤、工程规范或者检查规则时，就可以将它们提炼出来，封装成一个 Skill。

例如，经常重复出现的任务包括：

  • 创建相同的软件目录；
  • 编写统一格式的 README；
  • 生成 CMakeLists；
  • 检查软件分层；
  • 创建模块接口；
  • 检查命名规范；
  • 生成测试说明；
  • 初始化 Git 仓库；
  • 输出项目状态报告。

这些内容都可以逐步沉淀为 Skill。

工程师不一定需要从零手工编写整个 Skill，可以先将自己的实际需求告诉 Codex，例如：

请把我们每次创建嵌入式工程时需要重复执行的目录创建、文档生成、架构约束和检查流程，整理并封装成一个可复用的 Skill。

随后再通过实际项目不断测试、修改和完善。

最终，这些 Skill 将不再只是某一名工程师的个人使用习惯，而可以逐渐成为：

可重复使用、可持续改进、可供团队共享的工程能力。

6.3 理解 Hooks

Hooks 是在指定事件发生时执行的脚本，例如任务结束后提醒检查结果。它与按任务选择的 Skill 不同，启用前要确认触发时机、运行环境和命令内容。

要写清楚的内容示例
事件任务结束或某类工具执行前后。
动作运行已有检查脚本，输出结果。
失败处理提示失败并保留日志，不把失败当成功。
权限明确脚本会读写什么、是否访问外部服务。
可复制提示词
请根据当前环境支持的 Hooks，设计一个任务结束后的检查流程。
先说明触发事件、要执行的脚本、失败时如何提示，以及权限范围。
先给方案，不直接安装或执行。

参考：Hooks 与插件

6.4 理解 MCP

MCP 为模型连接外部工具与数据提供统一接口。一个服务可以提供读取 Issue、查找文档或修改记录等工具；具体能力取决于服务器实现、认证和授权。

概念关注点
工具这次可以执行什么动作？
连接由哪个服务处理请求？
认证使用哪个账号或凭据？
权限只读、写入和公开发布分别允许什么？

先用一个明确的只读任务验证连接，例如读取示例仓库的 README。写入或发布前，再核对具体目标和影响。

在 Codex 中，Plugin 可以理解为：

围绕某一类任务或工作流，将操作说明、外部工具连接和可重复执行能力打包在一起的功能模块。

当你安装插件或自己创造插件后，Codex 不仅知道“应该怎样思考和处理任务”，还可能获得访问外部数据、调用外部工具以及执行特定操作的能力。

例如，一个 GitHub 相关插件可能帮助 Codex：

  • 查询代码仓库；
  • 阅读源代码；
  • 分析提交记录；
  • 查看 Issue 和 Pull Request；
  • 总结项目近期变化；
  • 在获得权限和确认后执行部分仓库操作。

因此，Plugin 的作用并不是简单地给 Codex 增加一个按钮，而是让 Codex能够适应某一类真实工作流程，这也是其最核心的一个功能

那一个Plugin由什么组成呢？我想可以按照这么一个简单的框架来说明：

组成作用
Skill（可选）说明任务步骤、参考资料与输出格式。
MCP 或服务连接（可选）提供经过认证的外部工具与数据访问。
脚本、Hooks 与资源（可选）提供执行动作、事件响应或模板。

这是常见组合示意，不要求每个插件都同时包含这些部分。

那么实际的一个执行流程可以这么理解：

插件工作流程
理解目标 → 判断所需能力 → 检查工具与权限
→ 在授权范围内执行 → 核对返回结果 → 给出可审阅输出
