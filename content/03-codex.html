3.5 Codex 项目的创建与管理（二）：Git 与任务管理（像一个系统工程师一样去构建你的项目）

本节用于说明在使用 Codex 修改项目时，如何通过 Git、Worktree、Diff 等方式保证代码可追踪、可检查、可回退。

使用 Codex 处理代码任务时，不建议直接让 Codex 修改正式项目。正确流程应当是：

先确认 Git 状态 → 让 Codex 先分析 → 建立安全检查点 → 再允许小范围修改 → 查看 diff → 人工 Review → 编译或测试验证 → 再决定是否提交。

3.5.1 使用 Git 管理项目（推荐）

Git 是代码版本管理工具，用于记录项目修改历史。

在使用 Codex 修改项目之前，应先确认当前项目是否已经纳入 Git 管理。

使用 Git 的目的不是增加操作复杂度，而是为了做到：

  1. 知道 Codex 修改了哪些文件；
  2. 出现问题时可以回退；
  3. 修改前后可以对比差异；
  4. 方便后续人工 Review；
  5. 方便提交 commit 或创建 PR。

先判断项目是否已经 Git 化

打开项目后，可以先让 Codex 检查当前项目是否已经使用 Git 管理。

1.5 本节建议规则

使用 Codex 修改项目前，建议遵守以下规则：

  1. 没有 Git 的项目，先 Git 化或至少备份；
  2. 已有 Git 的项目，先检查 git status；

有未提交修改时，先识别并保留已有工作，选择合适的隔离方式与修改范围。

  1. 重要项目不要直接在主分支上操作；
  2. 允许 Codex 修改前，先建立 checkpoint；
  3. 修改完成后必须查看 diff。

一句话总结：

先让项目可追踪、可对比、可回退，再让 Codex 修改代码。

3.5.2 如何提交（推荐）

本节用于说明在使用 Codex 完成一个具体任务节点后，如何进行阶段性提交，以及出现问题时如何回退。

3.5.3 使用 Worktree 隔离修改

Worktree 可以理解为给同一个 Git 项目创建一个独立工作区。

使用 Worktree 后，Codex 可以在独立目录中修改代码，不会直接影响当前正在使用的项目目录。

适合使用 Worktree 的情况：

  • 当前项目已有未完成修改；
  • 不希望 Codex 直接改动当前工作区；
  • 需要让 Codex 尝试较大范围修改；
  • 想保留原项目目录不变；
  • 需要同时处理多个任务。

简单理解：

普通本地模式Codex 直接在当前项目目录中修改
Worktree 模式Codex 在独立工作区中修改，便于隔离和回退

推荐提示词：

可复制提示词

要求：
1. 不要直接修改我当前工作区；
2. 请在独立工作区中完成分析和修改；
3. 修改完成后说明改了哪些文件；
4. 不要自动合并到当前分支；
5. 等我确认后，再决定是否保留或合并。

注意：

  • Worktree 需要项目已经使用 Git 管理；

受 Git 管理的代码和文档都可以使用 Worktree；它隔离工作目录，但不等于文件访问权限沙箱。

3.7 Skill 编写与开源插件下载

3.7.1 Skill 是什么

Skill 是一套可以重复使用的工作流程。它通过说明文件、参考资料和可选脚本，告诉 Codex：

  • 什么情况下使用；
  • 按什么步骤执行；
  • 需要读取哪些资料；
  • 最终输出什么结果。

例如，可以制作“代码审查”“生成测试用例”“整理项目文档”“检查编译错误”等 Skill。

Codex通常先读取 Skill 的名称和描述，只有判断任务匹配时，才会继续读取完整的SKILL.md，因此能够减少无关上下文占用。

AGENTS.md负责长期工程规则，Skill负责可重复执行的具体流程。

3.7.2 什么时候需要写 Skill

出现以下情况时，适合制作 Skill：

  • 同类提示词需要反复输入；
  • 工作步骤基本固定；
  • 输出格式需要保持一致；
  • 团队成员需要执行同一套流程；
  • 任务需要结合模板、示例或脚本；
  • Codex经常遗漏某个固定步骤。

例如，每次代码修改后都需要执行：

可复制提示词
检查修改范围
→ 编译工程
→ 运行测试
→ 查看Git差异
→ 输出风险和未验证项

这类稳定、重复的流程适合封装成 Skill。

以下内容通常不必单独写成 Skill：

  • 只执行一次的临时任务；
  • 一句话就能说明的简单要求；
  • 整个项目始终必须遵守的固定规则。

项目级固定规则更适合写入AGENTS.md。

3.7.3 一个 Skill 目录应该包含什么

一个基础 Skill 至少需要一个SKILL.md文件，其他目录根据实际需要添加：

可复制提示词
code-review/
├─ SKILL.md
├─ scripts/
├─ references/
├─ assets/
└─ agents/
   └─ openai.yaml

各部分作用如下：

文件或目录作用
SKILL.md必需，定义名称、触发场景和执行步骤
scripts/可选，存放自动检查或处理脚本
references/可选，存放规范、示例和参考资料
assets/可选，存放模板、图片等资源
agents/openai.yaml可选，配置界面信息、调用策略和工具依赖

Codex支持将项目 Skill 放在：

可复制提示词
项目根目录/.agents/skills/

个人通用 Skill 可以放在：

可复制提示词
$HOME/.agents/skills/

项目目录中的 Skill 可以跟随Git一起管理，个人目录中的 Skill则可以在不同项目中重复使用。

3.7.4 SKILL.md 的基本写法

一个最基础的SKILL.md可以这样写：

可复制提示词
---
name: code-review
description: 检查代码修改范围、潜在缺陷和测试完整性。用于用户要求代码审查、提交前检查或风险分析时。
---

# 代码审查流程

1. 首先查看当前Git状态和代码差异。
2. 确认修改是否超出任务范围。
3. 检查接口兼容性、异常处理和潜在安全问题。
4. 检查是否存在无关格式化或文件删除。
5. 检查现有测试是否覆盖本次修改。
6. 不直接修改代码，除非用户明确要求。

# 输出格式

按照以下顺序输出：

1. 严重问题
2. 一般问题
3. 测试缺口
4. 修改建议
5. 未验证事项

文件开头必须包含：

可复制提示词
---
name: skill-name
description: 说明什么时候应该使用，以及什么时候不应该使用。
---

其中：

  • name是Skill的唯一名称；
  • description决定Codex能否正确识别使用场景；
  • 正文用于规定执行顺序、输入要求和输出格式。

官方建议一个 Skill只负责一类任务，并优先使用明确的文字步骤；只有需要确定性执行或调用外部工具时，再加入脚本。

3.7.5 如何让 Codex 正确触发 Skill

Codex可以通过两种方式调用 Skill。

手动指定

在提示词中直接输入：

可复制提示词
$code-review 请检查当前工作区的代码修改。

查看当前入口的技能列表；命令和选择器以该入口帮助为准。

自动触发

任务与 Skill 描述匹配时，可以自动选用。ChatGPT 可使用 @ 选择，Codex 可使用 $ 指定；按当前入口操作。

参考：Skill 与插件

为了提高触发准确率，description应写清楚：

  • Skill处理什么任务；
  • 常见触发词是什么；
  • 哪些情况不应该使用。

不推荐：

可复制提示词
description: 用于处理代码。

推荐：

可复制提示词
description: 用于检查Git代码差异、识别潜在缺陷和测试遗漏。用户要求代码审查、提交前检查或修改风险分析时使用；不用于直接开发新功能。

编写完成后，应分别测试：

可复制提示词
应该触发：请审查当前代码修改。
应该触发：提交之前帮我检查风险。
不应触发：帮我开发一个登录页面。

如果不希望Codex自动调用，还可以在agents/openai.yaml中关闭隐式调用，只允许用户通过$skill-name手动触发。

3.7.6 Plugin、Skill、MCP 的关系

三者承担的职责不同：

类型主要作用通俗理解
Skill定义重复执行的流程告诉Codex“怎么做”
MCP连接外部工具和数据给Codex提供“可以使用的工具”
Plugin打包和分发Skill、连接器及MCP把能力组合成“可安装产品”

例如，一个“项目问题处理插件”可以包含：

  • 一个问题分析 Skill；
  • 一个代码修改 Skill；
  • 一个GitHub MCP连接；
  • 一套输出模板。

Skill负责规定处理步骤，MCP负责读取GitHub问题或执行操作，Plugin负责把这些能力统一安装和分发。

可以简单记忆为：

Skill定义流程，MCP连接工具，Plugin负责打包和安装。

3.7.7 安装插件时的注意事项

正确安装方式

在Codex CLI中可以输入：

可复制提示词
/plugins

Codex CLI 安装插件后开启新会话。桌面和网页端按插件目录操作；当前官方说明 IDE 扩展不支持插件。

参考：插件支持范围

安装单独的本地Skill时，可以使用：

可复制提示词
$skill-installer

也可以让安装器从指定仓库获取Skill。

安装前重点检查

  1. 确认来源可靠

优先使用OpenAI官方、团队工作区或可信开发者提供的插件，避免随意运行来源不明的脚本。

  1. 检查权限范围

确认插件是否需要：

  • 读取项目文件；
  • 执行终端命令；
  • 连接GitHub或云盘；
  • 修改外部数据；
  • 使用网络和账号权限。
  1. 检查脚本与Hooks

插件可能包含自动执行的生命周期Hooks。启用前应查看其命令内容，避免运行删除文件、上传数据或修改系统配置的操作。Codex不会因为插件已安装就自动信任其Hooks，仍需要用户审查和授权。

  1. 不要写入敏感信息

不要把密码、API Key、Token和账号凭据直接写进：

可复制提示词
SKILL.md
脚本文件
配置示例
Git仓库

认证通过服务授权流程或受控的本地凭据输入完成；避免把秘密复制进聊天、公开命令示例或仓库。

  1. 先在测试项目中验证

首次安装插件后，先确认：

  • 是否正确触发；
  • 实际调用了哪些工具；
  • 是否修改了预期之外的文件；
  • 能否正常停止和回退；
  • 输出是否符合项目要求。

安装插件的原则不是“功能越多越好”，而是来源可信、权限最小、过程可审查、结果可验证。

3.8 常见问题

3.8.1 无法登录 / 手机验证失败

先核对账号、登录方式、入口和完整错误提示；按当前官方验证流程处理，订阅套餐或特定号码不保证解决问题。

3.8.2 看不到 Codex 入口

检查所用客户端、工作空间、套餐和管理员设置；从官方说明查找当前可用入口，不依赖旧截图中的固定按钮。

3.8.3 VS Code 扩展不显示

检查扩展是否已安装和启用、编辑器是否需要重启；区分扩展本身与插件目录的支持范围。

3.8.4 Codex 不能读取项目

核对当前目录、文件访问权限及实际可用工具；先让它只读列出可访问资料，避免对错误项目开始修改。

3.8.5 Codex 改错文件怎么办

先停止继续叠加修改，查看 git status 和 diff，区分本次改动与原有工作；针对确认的文件决定修复或恢复。

3.8.6 额度消耗过快怎么办

核对实际用量，缩小无关上下文与任务范围，避免重复无目标尝试；按难度选择模型和推理强度。

3.8.7 修改后如何回退

先保存当前需要保留的工作，再核对目标提交与文件范围。对已共享提交优先考虑可追踪的撤销方式；不要未经核对直接执行破坏性重置。

3.8.8 什么时候应该停止让 Codex 继续改

当改动持续偏离目标、重复失败、证据不足或可能影响设备和数据时，先停止执行并整理当前状态、日志与待确认问题。
